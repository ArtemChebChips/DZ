# Исправления «ДЗ» после проверки на iPhone

План от 21 сентября 2026 по замечаниям владельца. Исходная версия — 1.23.1, ветка `codex/rebuild`, приложение находится в `design/`. Владелец подтвердил на iPhone верхний отступ и стабильность панели P1; уменьшение нижнего зазора и выравнивание заголовков выпущены в 1.23.3. P2 реализован в 1.23.4 и проверен в браузере. P3–P4 реализованы в 1.23.5; P5–P6 реализованы в 1.23.6. Браузерная часть P7 пройдена; проверка установленного приложения на настоящем iPhone остаётся открытой. [Итоговый отчёт](design/implementation/P5-P7.md).

Этот план задаёт ближайший порядок работы вместо продолжения редакторов предметов и расписания из общего [плана перезапуска](REBUILD_PLAN.md). Выполняем по одному этапу: реализация, проверки, коммит, push, проверка публикации. Владелец поручил пройти оставшиеся P3–P7 без остановки; это разрешение относится к текущему плану исправлений. Готовые запросы для Astra на Medium — в [ASTRA_WORKFLOW.md](ASTRA_WORKFLOW.md).

## Что установлено

| Наблюдение | Что видно в текущем коде |
|---|---|
| Заголовок попадает в верхнюю область iPhone | В `design/index.html` есть `viewport-fit=cover`, но верхний отступ `.app-main` — фиксированные 36 px без верхнего safe area. Это пробел в вёрстке; полный сценарий установленного приложения нужно проверить отдельно. |
| Нижняя панель прыгает между вкладками | Панель общая и фиксированная, экраны разной высоты; при переключении вызывается прокрутка к началу. Нижние отступы есть у содержимого и панели. Причина скачка по одному коду не доказана: нужны измерения видимой области, прокрутки и положения панели. |
| В расписании сначала виден календарь | Месячная сетка постоянно находится перед списком пар в `design/main.tsx`. |
| Системный выбор предмета, длинные названия | Редактор использует `<select>` и полные `name`; остальные экраны — `short`. |
| Лекции подсвечиваются вместе с подходящими парами | У общего редактора часто не задан `kind`; поиск тогда включает все виды занятий. Календарь получает только признак «есть занятие», без разделения семинаров и лаб. |
| Задание оказывается под расписанием | Общий редактор может сохранять задачу без `kind` и `lessonId`. Такая запись не привязывается к паре. При нескольких одинаковых занятиях текущий выбор первой подходящей пары тоже недостаточен. |
| Время мелкое, показаны корпуса | `.lesson-time` имеет размер 15 px; отдельной строкой выводится `building`. Поле `teacher` в исходных данных есть, но заполнено не у всех пар. |
| Дата может устареть после полуночи | `TODAY` вычисляется при загрузке модуля. Возвращение в давно открытое приложение само по себе не обновляет этот день. |

Проверка исходников не доказывает устранение ошибки на устройстве. В результате каждого этапа отдельно отмечаем браузерную проверку и результат на настоящем iPhone.

## Принятые решения

- Сохраняем направление [A4 «Лист»](design/concepts/round-2/a4.png): светлая основа, спокойная типографика, тонкие разделители, синий акцент, минимум вложенных плашек. A4 — обозначение выбранного варианта; размеры интерфейса определяет экран телефона.
- Просьба о расписании дня имеет приоритет над календарём сверху на картинке. Новые концепции ImageGen сейчас не нужны.
- Состав и время пар, виды занятий, преподавателей, аудитории, идентификаторы и чередование недель от `2026-08-31` сохраняем. Корпуса скрываем в интерфейсе, исходные сведения не удаляем.
- Домашнее задание относится к семинару или лабораторной. Для произвольного дня будет простой режим заметки, в том числе с необязательным предметом.
- Старые задания, включая записи без привязки и прежние задания к лекциям, сохраняем. Дата меняется только по действию пользователя; переименование предмета или правка расписания её не сдвигают.
- Работаем с текущим `dz-next:v1`; старые `dz:*` не трогаем. Новые поля должны быть совместимы с сохранениями 1.23.1. Сервер, синхронизация, новый UI-фреймворк и перенос прежней базы в этот план не входят.
- Настройки сохраняют текущий вид; добавляется только вход «Для бета-тестеров». Общие названия предметов обновляются везде.

## P1. Верхняя область и нижняя панель

**Результат реализации, 21 сентября:** общий экран имеет высоту видимой области; прокручивается только `main`, нижняя панель занимает отдельную строку. Добавлены верхние и боковые безопасные отступы; нижний отступ панели учитывается один раз. Редактор подстраивается под видимую область и оставляет активное поле над кнопкой сохранения. Версия 1.23.2. [Проверки и ограничения](design/implementation/P1.md). Коммит определяется по версии: `git log --grep='1.23.2'`.

**Результат:** заголовок находится под системной областью; навигация занимает одинаковое место во всех трёх вкладках, без лишней пустой полосы и перекрытия содержимого.

1. Зафиксировать поведение пустых «Задач», коротких «Настроек» и длинного «Расписания». Сравнить размеры видимой области, положение панели, высоту документа и прокрутку до/после переключения. Отдельно учитывать Safari с адресной строкой и запуск по домашнему ярлыку.
2. Исправить общую оболочку: согласовать верхний безопасный отступ, высоту страницы, положение навигации и место под неё в прокручиваемом содержимом. Проверить боковые безопасные области в горизонтальном положении.
3. Выбрать одну понятную схему прокрутки. Безопасный отступ не должен складываться повторно внутри одной области; резерв места под фиксированной панелью должен соответствовать её фактической высоте.
4. Проверить модальные окна и клавиатуру: после закрытия редактора навигация возвращается в исходное место. Поля и кнопка сохранения остаются доступны.

Основные места: `design/style.css`, оболочка и `changeTab` в `design/main.tsx`, при необходимости метаданные в `design/index.html`. Изменение режима status bar или применение `dvh` должно следовать проверке, а не быть случайным набором CSS-поправок. Без фиксированных «поправок под конкретный iPhone».

**Приёмка:** одинаковая координата нижней панели при переключении вкладок в одном состоянии экрана; верхний заголовок и последняя строка списка доступны; нет горизонтальной прокрутки. Пустой и длинный списки, открытие/закрытие клавиатуры и поворот экрана не оставляют смещения.

**Проверки:** браузер на 375/390/430 px и широком экране, обе темы, повторные переключения вкладок и прокрутка. На реальном iPhone — старый ярлык, Safari, клавиатура и повторное открытие. Если устройство недоступно, опубликовать проверенное браузером исправление и явно оставить подтверждение на iPhone открытым.

Официальное объяснение `viewport-fit=cover` и безопасных отступов: [WebKit — Designing Websites for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/). Оно объясняет принцип, но не устанавливает причину нынешнего скачка панели.

## P2. Расписание открывается на сегодня

Реализован в 1.23.4. [Результат и проверки](design/implementation/P2.md). Новый экран и компактный нижний отступ ещё нужно оценить на iPhone.

**Результат:** при переходе на вкладку сразу видны сегодняшняя дата и пары; постоянной месячной сетки сверху нет.

1. В шапке оставить дату, день недели, обозначение учебной недели и кнопку «Календарь». Под ней — список пар на доступную высоту страницы с прокруткой при длинном дне.
2. По кнопке открыть собственный календарь. Нажатие дня закрывает календарь и показывает этот день; отмена оставляет прежний день. Дать кнопку «Сегодня», если открыт другой день. Пустой день показывает короткое сообщение.
3. При переходе из другой вкладки открывать сегодня. Закрытие календаря или редактора внутри вкладки сохраняет выбранный день. После полуночи обновлять локальную текущую дату, в том числе при возвращении в приложение; незаконченный черновик и сохранённые сроки не менять.
4. Время начала и окончания сделать заметнее: ориентир 18–20 px на телефоне, с достаточной шириной колонки. Предмет и задания остаются главной частью строки.
5. У пары показывать вид занятия, `Каб. 327.1` или другую реальную аудиторию, а при наличии — фамилию преподавателя с инициалами. Для `каф. ФН4` сохранить осмысленный текст без выдуманного номера кабинета. Нескольких преподавателей не терять. Коды корпусов скрыть.

Основные места: расписание в `design/main.tsx`, `Calendar`/`Modal` в `design/components.tsx`, `design/style.css`, получение текущей даты в `design/data.ts`. Переиспользовать существующие календарь и функции дат.

**Приёмка:** вход в расписание сразу показывает пары сегодня; можно выбрать дату и вернуться; время и кабинет не обрезаются на узком экране. Преподаватель выводится только при наличии данных. Содержание расписания совпадает с исходным.

**Проверки:** будний день, воскресенье без пар, обе учебные недели, длинный ВУЦ, переход месяца и возвращение после смены локального дня. Сверить реальные пары с `src/data/schedule.ts`, включая нестандартное время. Повторить проверку панели из P1.

Основные места: `design/components.tsx`, `design/data.ts`, `design/style.css`. Идентификаторы и исходные данные старой версии остаются совместимыми.

**Проверки:** мобильный браузер, клавиатура на компьютере, обе темы, редактирование существующей задачи и задачи без предмета. На iPhone подтвердить отсутствие системного селектора.

## P4. Календарь домашних заданий и привязка к паре

**Результат:** календарь показывает семинары синим и лабораторные зелёным; сохранённое задание появляется внутри нужной пары. Выбор и сохранение используют одинаковые правила.

1. Сделать небольшую общую функцию подходящих занятий на дату: нужный предмет, реальное чередование недель, вид `seminar` или `lab`. Использовать её в подсветке, выборе пары и проверке привязки. Лекции остаются в расписании, но исключаются из новых домашних заданий и быстрых предложений даты.
2. Вместо логического `match` передавать календарю информацию о семинарах и лабах. Если в день есть оба вида — показать оба маркера. Легенда «Семинар / Лаба» и доступные подписи дополняют цвет. Выбранный день и «сегодня» различаются с маркерами занятий, в том числе в тёмной теме.
3. В общем редакторе показывать доступные виды занятий. При единственном виде выбирать его автоматически; при двух предлагать «Семинар / Лаба» явно. Календарь сохраняет видимость обоих видов. При выборе дня с другим видом предложить сменить вид, а не скрыто назначать другую пару. Если кандидатов несколько, нужен короткий список с видом и временем.
4. Для двух лабораторных одного предмета за день предлагать конкретное время. Не выбирать молча первую. Массовую привязку к нескольким парам сейчас не вводим.
5. Создание из строки пары сразу заполняет предмет, вид и пару. У лекций убрать кнопку создания ДЗ. Быстрые даты искать по выбранному виду и учебной неделе; подписи должны обозначать вид и следующую дату занятий. Две лабы одного дня выбираются списком времени.
6. Сохранять `subjectId`, `kind`, `lessonId` и `due`. При смене даты проверять прежнюю привязку; если возможны несколько замен, нужен явный выбор. Дата без подходящей пары допускает запись без привязки с понятной подписью; после P5 её можно создать как заметку дня. Скрытого переноса срока нет.
7. В расписании помещать задачу в блок конкретной пары на её дате. Редактирование, выполнение и удаление работают там же; та же запись видна в «Задачах», без дублирования в хранилище.
8. Для старых записей сначала учитывать действительную явную привязку. Без неё разрешён подбор только единственного подходящего семинара/лабы по дате, предмету и известному виду. При неоднозначности или исчезнувшей паре оставить запись на её дате в секции «Без привязки к паре» с действием выбора пары. Не назначать случайно первую лабу или лекцию. Существующее задание, явно привязанное к лекции, остаётся доступным; запрет касается создания нового ДЗ.

Основные места: тип записи в `design/data.ts`, редактор и календарь в `design/components.tsx`, сохранение/распределение в `design/main.tsx`, проверки в `tests/`. Небольшой модуль расчёта привязок допустим, если убирает дублирование. Универсальную библиотеку расписаний не строим.

**Приёмка:** общий редактор и создание из пары дают корректную привязку; семинар не попадает к лекции; две лабы различимы; ни одна старая задача не исчезает. Привязанные задания больше не выводятся общим списком под расписанием. Исключение «Без привязки» — для записей, которые нельзя сопоставить безопасно.

**Проверки логики:** на настоящих данных физика 21.09.2026 — семинар 15:55 и лекция 14:05; 28.09.2026 — две лабы 15:55 и 17:35. Дополнительно фикстура с семинаром и лабой одного предмета в один день, предмет только с лекциями, дата без занятий, обе учебные недели и переход месяца. Проверить старые записи без новых полей, отсутствующую пару, сохранение и повторное открытие, неизменность срока после правки фикстуры расписания. Новые проверки включить в `npm run test:next`, чтобы их запускал workflow.

## P5. Заметка на выбранный день

**Результат:** можно записать личное дело или редкое поручение с лекции на произвольную дату без фиктивной привязки к семинару.

1. Добавить в расписание действие «Заметка на день». В общем редакторе дать явный выбор между ДЗ и заметкой; использовать ту же простую форму текста и даты.
2. У заметки предмет необязателен, пара не выбирается. Она видна в отдельной компактной секции дня и в общем списке по сроку, поддерживает редактирование, выполнение и удаление. Календарь заметки не ограничен днями занятий.
3. Различать запись дня и ДЗ одним простым признаком, без отдельного хранилища. Новое необязательное поле проверить при чтении и сохранить в резервной копии. Старые личные задачи продолжить показывать как записи дня; неоднозначное старое ДЗ не превращать молча в заметку.

Основные места: `design/data.ts`, `design/storage.ts`, редактор и расписание. Это короткая запись с текстом; вложения, богатый редактор и отдельная вкладка заметок не нужны.

**Приёмка:** на день без пар можно добавить запись; она находится в расписании дня и «Задачах», переживает перезапуск и не попадает внутрь случайной пары. ДЗ остаётся внутри своей пары.

**Проверки:** заметка без предмета и с предметом, воскресенье, правка даты, выполнение/возврат, перезапуск, чтение старой базы и экспорт новых полей.

## P6. Раздел для бета-тестеров

**Результат:** в настройках есть вход «Для бета-тестеров», внутри две кнопки: «Добавить тестовые задания» и «Удалить тестовые задания (N)».

1. Генерировать небольшой набор, ориентир 20–30 записей от сегодня на три недели вперёд. Использовать реальные даты семинаров/лаб и корректные связи с парами; добавить несколько записей дня, длинные и короткие тексты, выполненные и невыполненные задачи. Даты считать от текущего локального дня устройства.
2. Каждой созданной записи присваивать явную служебную отметку, например необязательный `testBatchId`. Не определять тестовые записи по тексту, ID-префиксу или предмету. Отметка переживает правку, сохранение, перезапуск и экспорт; валидатор проверяет её тип.
3. Повторное нажатие заменяет только предыдущий отмеченный набор новым, сохраняя личные задания. Интерфейс заранее сообщает это поведение. Сгенерировать и проверить весь набор перед одной записью в хранилище.
4. Удаление убирает только отмеченные записи, в том числе выполненные и отредактированные. Личные записи, тема, свёрнутые дни и расписание остаются. Показать число удалённых; при отсутствии тестовых записей кнопка неактивна.
5. Генератор работает по нажатию в обычном приложении. Демо `?demo=1` по-прежнему изолировано и не меняет рабочую базу. При ошибке загрузки/сохранения не показывать ложный успех.

Основные места: настройки в `design/main.tsx`, небольшой генератор, типы и `design/storage.ts`. Для тестов передавать фиксированные дату и источник случайности; в приложении варианты меняются. Новая зависимость для случайных данных не нужна.

**Приёмка:** набор можно осмотреть на нескольких неделях; повторное добавление не размножает старые примеры; очистка не удаляет личные задачи даже с одинаковым текстом. После перезапуска примеры всё ещё удаляются этой кнопкой.

**Проверки:** смесь личных/тестовых записей, добавление дважды, правка тестовой записи, перезапуск, очистка, повреждённые сохранения, ошибка записи. Проверить допустимые даты/пары и полное сохранение личных записей после очистки.

## P7. Согласованность дизайна и итоговый проход

**Результат:** новые элементы выглядят частью A4 «Лист», а основные действия проходят подряд в опубликованной версии.

1. Сравнить реальные снимки с референсом: иерархию текста, даты, время пар, разделители, плотность и навигацию. Использовать одинаковые данные там, где возможно. Изменённая по просьбе владельца композиция расписания ожидаема.
2. Проверить три вкладки, календарь, список предметов и редактор в обеих темах на 375/390/430 px и широком экране. Устранить обрезания текста, недоступные кнопки и незаметное выбранное состояние. Не уменьшать шрифт ради размещения корпуса или длинного названия в одну строку.
3. Пройти сценарий: создать ДЗ → выбрать семинар/лабу → увидеть его внутри правильной пары → изменить срок → выполнить → вернуть; затем заметка дня → тестовый набор → очистка → перезапуск.
4. На старом ярлыке iPhone проверить положение панели, системную верхнюю область, клавиатуру, открытие календаря и отсутствие системного выбора предмета. Записать модель устройства/iOS, если доступны, и фактический результат. До этой проверки не называть проблемы установленного приложения подтверждённо закрытыми.

При расхождениях исправить их в пределах выбранного дизайна и выпустить обновление. Если код уже проходит проверки, не делать фиктивное повышение версии ради отметки о проверке.

## Проверка и выпуск каждого изменения приложения

1. Проверить ветку и чужие незакоммиченные изменения. Прочитать выбранный этап и относящиеся к нему файлы; остальные документы — по конкретному вопросу.
2. Проверить затронутые пользовательские сценарии. Для P4–P6 добавить небольшие проверки правил и сохранности данных; для CSS и текста достаточно осмотра интерфейса, без тестов, повторяющих стили.
3. Поднять версию в `package.json` и `package-lock.json`, проверить новую сборку `npm run build:design` и набор `npm run test:next`. Если меняется общий код, проверить затронутую старую сборку. Успешные проверки не повторять без новых изменений или выявленной проблемы.
4. Сделать коммит законченного изменения и сразу push `codex/rebuild`; дождаться результата Pages. Проверить публикацию нужного коммита и версию по [старому адресу приложения](https://artemchebchips.github.io/DZ/); `/next/` содержит ту же сборку. Не заменять адрес для телефона локальным превью.
5. Записать результат этапа, версию, коммит и проверки. В отчёте владельцу — краткий результат, ссылка, версия, коммит, что действительно проверено и что требует iPhone. Разрешение на обычные проверки, коммит, push и публикацию уже есть.

Рабочие данные владельца для тестов не очищать. Использовать изолированный профиль браузера/фикстуры; `?demo=1` подходит для вида, но постоянное хранение отдельно проверяется на тестовой базе.
