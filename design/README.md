# Новая версия ДЗ для iPhone

Текущая версия указана в `package.json` и в разделе «О приложении». Дизайн выбран по варианту A4 «Лист» — это название концепции, не формат бумаги. Актуальное описание проекта — `docs/PROJECT_OVERVIEW.md`, результаты аудита — `audit/PROGRESS.md`.

Публикация: https://artemchebchips.github.io/DZ/ . Каждый push в codex/rebuild запускает сборку всех версий и публикацию Pages.

- `npm run dev:design` — локальный сервер (только на компьютере).
- `npm run build:design` — сборка нового приложения в dist-design.
- `npm run test:next` — проверки хранения, валидации и ошибок доступа.

Обычный запуск использует текущую дату и сохраняет задания, тему, скорость анимаций и свёрнутые дни в `dz-next:v1`. Изменения сохраняются при каждом действии; редактор ждёт завершения записи. Окна одного origin получают обновления друг друга. При ошибке записи доступна копия несохранённых данных страницы. Старые ключи `dz:*` не читаются и не меняются. Можно скачать JSON-копию. Импорт и редактирование расписания/предметов ещё не подключены. Manifest поддерживает ярлык iPhone; после успешной установки service worker приложение работает офлайн.

Для примеров: `?demo=1`, `?demo=1&fixture=stress`, `?demo=1&fixture=empty`. Демо работает только в памяти, дата — 21 сентября 2026. Без параметра `screen` открывается расписание на сегодня. Явные `screen=tasks`, `screen=schedule` и `screen=settings` открывают соответствующую вкладку; возврат из фона не сбрасывает выбранный день или открытый редактор.

Старый ярлык iPhone открывает новую версию в корне. `/next/` остаётся дополнительным адресом, прежний интерфейс — `/legacy/`. Worker отдаёт установленную оболочку из кеша и устанавливает обновления в фоне, без автоматической перезагрузки открытой формы. Корень и `/next/` имеют отдельные кеши и общий notebook на одном origin. Dev и demo не регистрируют worker; для production preview используй отдельный порт.

С 1.23.60: «Настройки → Диагностика запуска» показывает этапы открытия и копирует текущий запуск вместе с четырьмя предыдущими. История хранится отдельно в `dz-next:startup:v1`; тексты заданий и другие рабочие данные туда не попадают. Автоматической отправки нет. Демо не читает и не пишет историю диагностики. Автоматическая запись выполняется после оценочного кадра; открытие отчёта также обновляет доступные замеры, если Safari приостановил rAF в фоне.

`pageScript`, `mainModule`, `interfaceCommit`, `frameEstimate`, Navigation/Paint Timing считаются от `performance.timeOrigin`. Чтение темы и notebook отмечается до/после существующих операций, без дополнительных чтений базы. `frameEstimate` — двойной rAF, не доказательство показа пикселей. Если Paint/Server Timing недоступны, отчёт не подменяет их нулём или оценкой. Время от касания ярлыка до начала навигации может отсутствовать. Поэтому наблюдаемые владельцем 7 секунд сравниваются с отчётом, а не объявляются измеренными автоматически. Заголовок Server-Timing содержит источник HTML и версию/build отдавшего его worker; отдельное сообщение после запуска проверяет текущий controller. Проверки: `tests/startup.test.mjs`, браузер на мобильной ширине, открытие из кеша при остановленном сервере и Safari на Mac. Физический холодный запуск на iPhone остаётся проверкой владельца.

С 1.23.61 раннее чтение темы удалено. HTML содержит статическую оболочку «ДЗ / Открываем…» с собственной небольшой таблицей стилей. До чтения notebook браузер получает два rAF и отдельную задачу; при поддержке Paint Timing дополнительно ждём запись FCP (не более 100 мс после второго rAF). Если API недоступен, остаётся оценка по кадрам. В скрытой вкладке сначала ждём возобновления кадров. Рабочая база читается один раз при начальном рендере, после оболочки. Её данные, сохранённая тема и скорость анимаций применяются вместе; перед чтением используются системные цвета (в демо — тема из URL). Пустая база не сохраняется при запуске или ошибке чтения.

`shellFrameEstimate` — оценка кадра оболочки, `appRenderStart` — передача управления React после неё, `themeApplied` — применение темы из notebook. FCP теперь может относиться к оболочке, а `interfaceCommit` и `frameEstimate` по-прежнему относятся к приложению с данными: сравнивать один FCP с прежней готовностью приложения нельзя. В `shell` добавлены отметки `workerScriptStart`, `fetchEventStart`, `responseReady` и длительности `cacheOpenMs`, `cacheMatchMs`. Отметки worker передаются как `performance.timeOrigin + performance.now()` и приводятся к началу навигации страницы; уже запущенный worker даёт отрицательный `workerScriptStart`. `responseReady` ставится перед созданием ответа, без чтения его тела; последующую передачу/обработку HTML ещё нужно сопоставлять с `pageScript`. Это разделяет исследуемое ожидание до страницы, но не измеряет системное время от касания ярлыка. Старые отчёты совместимы, отсутствующие новые поля показываются как «Нет замера».
