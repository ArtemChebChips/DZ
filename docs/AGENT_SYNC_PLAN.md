# Голосовой агент и синхронизация

Начато 1 октября 2026. Изолированная ветка `codex/agent-sync`, основа `c218703`
из `codex/rebuild`. Параллельный аудит и рабочая папка владельца не изменяются.
Прямое поручение владельца разрешает агент и синхронизацию; публикация и объединение
с `main`/`codex/rebuild` пока не разрешены.

## Результат

На iPhone: микрофон → запись → Parakeet v3 → Claude Haiku → задания с проверяемыми
предметами и сроками. Неоднозначности требуют уточнения. Первоначальный режим —
подтверждение карточек; автоматическое добавление включается отдельно и допускает отмену.
Аккаунт восстанавливает задания на другом устройстве. Ручной ввод работает офлайн.

## Этапы

1. Сверить существующий пилот, сохранить его контракты и локальный запуск на Mac.
2. Подготовить Linux CPU-распознавание Parakeet v3 через sherpa-onnx INT8,
   переиспользование модели, лимиты аудио и удаление временных файлов.
3. Добавить небольшой Python-сервис, SQLite, личные аккаунты, отзываемые сессии,
   проверки доступа, HTTPS и резервное копирование.
4. Реализовать синхронизацию отдельных записей: локальная очередь, серверные ревизии,
   идемпотентные операции, отметки удаления, явное разрешение конфликтов.
5. Подключить настройки аккаунта, безопасное восстановление JSON, голосовой сценарий
   и автоматический разбор после остановки записи, сохранив оформление «Лист».
6. Проверить два устройства, офлайн, повторы, конфликты, миграции и ошибки;
   отдельно принять реальные модели, Safari и установленную PWA на физическом iPhone.
7. Версия, lock-файл, сборка, коммиты и push только `codex/agent-sync`.
   Перед push сверить workflow. Никакой автоматической публикации.

## Данные и границы

- `dz-next:v1` и формат Notebook v1 сохраняются. Синхронизационные сведения добавляются
  совместимым необязательным полем; прежние ID, даты, задания и настройки не меняются.
- Перед первой привязкой аккаунта сохраняется исходная локальная копия. Повторная
  привязка и миграция не создают дубликатов. Повреждённые данные не перезаписываются.
- Личные записи из другого аккаунта не отправляются при смене пользователя.
- Демо и ключи прежнего приложения `dz:*` не участвуют в рабочей синхронизации.
- Расписание и якорь `2026-08-31` остаются источником вычисления сроков. Уже выбранный
  срок не меняется от правки расписания. Оформление и свёрнутые группы локальные.
- Никаких инструментов и записи в базу у Claude; только проверяемый JSON.
- Секреты, базы, аудио, личные копии и кеши моделей не входят в Git.
- Отдельные порты: интерфейс 4185, сервер 4286; проверять занятость перед запуском.
  Порт 4186 занят параллельной работой, её процесс не изменяли.

## Сервер и внешние зависимости

Стартовый кандидат: Linux x86-64, 2 vCPU, 4 ГБ RAM, 30–50 ГБ SSD, без GPU,
с увеличением до 4 vCPU / 8 ГБ после замера реальных записей. Это оценка, не SLA.
На Linux MLX не используется. Claude работает у провайдера через существующий
`claude -p` и подписку, с отдельным входом на сервере; платный API не подключается
без согласованного бюджета. Перед развёртыванием повторно проверить условия и регион.

Сервер не нужен для локальной разработки. Для приёмки развёртывания требуются VPS,
SSH-доступ, HTTPS-домен и авторизация Claude; эти данные владелец предоставит позже.

## Проверки и статус

Обязательные команды: `npm run test:next`, `npm run build:design`, тесты сервера.
Нужны сценарии: старая записная книжка, первый вход при пустом сервере, два устройства,
сеть пропала, повтор операции/ответ потерялся, конфликт правок, удаление, смена аккаунта,
ошибка localStorage, импорт/экспорт и повторный импорт. Устройство и реальные провайдеры
не заменять моками в окончательной приёмке.

На начало: локальный голосовой пилот есть; серверной синхронизации и телефонной приёмки нет.
Дальнейшие фактические результаты фиксируются в отчёте этой ветки.
