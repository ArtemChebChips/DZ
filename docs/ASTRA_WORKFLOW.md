# Как работать над «ДЗ» с GPT-6 Astra на Medium

Проверено по официальной документации OpenAI 19 сентября 2026. Здесь Astra — модель помощника в Codex; в само приложение никакой AI API добавлять не нужно.

У GPT-6 Astra поддерживается уровень рассуждения `medium`. Для этого проекта начинаем с выбранного владельцем Medium. Это рабочий выбор для наших итераций, а не обещание одинакового качества на любой задаче. Настройки модели автоматически не меняем. [Модель GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra).

## Что говорят рекомендации OpenAI

Для Astra особенно полезно заранее определить, какой результат считается завершённым, и разрешить обычные действия внутри задачи. Модель чувствительна к указаниям в `AGENTS.md` и навыках; противоречивые или чрезмерные инструкции могут вызывать лишние остановки. Объём проверок стоит соотносить с изменением. [Рекомендации для GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra).

Постоянные инструкции должны быть короткими и относиться к реальным правилам проекта. Не нужно заставлять модель перечитывать всю документацию перед каждой маленькой правкой. [Обновлённые рекомендации по навыкам и промптам Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

Промпт можно писать обычным языком. Для большой задачи достаточно указать цель, нужный контекст, ожидаемый результат и существенные границы. К визуальному примеру полезно добавить, что именно в нём нравится. [Постановка задач в Codex](https://learn.chatgpt.com/docs/prompting).

Практическое следствие для «ДЗ»: конкретный экран или сценарий, видимый результат, несколько критериев готовности и разрешение довести работу до проверки/коммита/push. Простыня с ролями и десятками повторяющихся запретов не нужна. Отдельной обязательной формулы промпта именно для Medium в изученных материалах нет.

## Шаблон обычной задачи

```text
Сделай [конкретное изменение] в «ДЗ».
Контекст: [этап плана, экран, при необходимости референс].
Ожидаемое поведение: [что пользователь увидит или сможет сделать].
Готово, когда: [2–4 наблюдаемых критерия].
Рутинные решения принимай самостоятельно. Доведи до проверки,
исправь найденные проблемы, сделай коммит и push рабочей ветки.
В конце коротко напиши результат и что проверено.
```

Правила простоты, русского языка, сохранения данных и Git уже записаны в `AGENTS.md`; каждый раз повторять их не требуется. Если задача исследовательская, прямо попроси исследование и результат в виде плана. Если нужна реализация, прямо попроси сделать и показать работающий результат.

## Следующий запрос: варианты дизайна

```text
Сделай этап 1 из docs/REBUILD_PLAN.md: три разных варианта дизайна «ДЗ».
Это учебный планер для меня и пары друзей, основной экран — iPhone.
Три вкладки: Задачи, Расписание с календарём, Настройки.

У каждого варианта покажи все три вкладки и редактор задания
на одинаковых демоданных. Варианты должны отличаться композицией,
типографикой и плотностью, чтобы между ними был реальный выбор.
Крупные читаемые сроки обязательны; длинный предмет не должен их скрывать.

Сделай отдельное интерактивное превью без рабочего хранилища и PWA.
Покажи мобильные изображения: название и описание перед каждым.
Дай свою рекомендацию по удобству. Проверь отображение в браузере,
исправь видимые проблемы, сохрани результат коммитом и push.
Закончи на готовом сравнении вариантов — окончательный выбор сделаю я.
```

На первом сравнении оцениваем три вещи: за несколько секунд понятен ближайший срок; добавить задание легко; расписание и календарь читаются без объяснений. «Нравится» тоже нормальный критерий, но конкретная обратная связь быстрее приводит к нужному виду.

## После выбора варианта

```text
Выбираю вариант B. Из A возьми только колонку крупных дат.
Доработай выбранный вариант по этапу 2: три вкладки, редактор,
светлая и тёмная темы, пустые и заполненные состояния.
На 375 px срок должен быть виден даже у длинного названия предмета.
Проверь также широкий экран. Покажи работающий результат и изображения.
Сделай коммит и push; рабочие данные подключим на следующем этапе.
```

Это пример формулировки; выбор B пока не сделан. Полезнее сказать «дата нравится в A, плотность в B, цвета в C», чем просить ещё раз «сделать красиво» без ориентиров.

## Реализация отдельного сценария

```text
В выбранном интерфейсе реализуй добавление задания с семинара.
Предмет и выбранная пара уже известны. По умолчанию дата — открытый день.
«Следующая пара» ищет следующий семинар с учётом числителя/знаменателя.
После сохранения задание должно быть видно у нужной пары,
а повторное открытие редактора должно сохранять этот контекст.
После удаления пары задание остаётся на своей дате.
Проверь сценарий на дне с лекцией и семинаром одного предмета,
сохранение после перезапуска и отсутствие дублей. Сделай коммит и push.
```

## Исправление конкретного недостатка

```text
На вкладке «Задачи» при ширине 375 px длинное название предмета
вытесняет срок сдачи. Дай сроку отдельное место в утверждённом дизайне.
Готово, когда название может занимать две строки, а срок всё равно виден;
остальные строки списка остаются ровными. Проверь короткую и длинную
задачи в обеих темах, затем сделай коммит и push.
```

Для сложной ошибки дай шаги воспроизведения и ожидаемый результат. Если неясно, что сломалось, сначала поручай установить причину, а не переписывать большой кусок наугад. Если выбранного Medium недостаточно для сложной диагностики, повышение уровня можно обсудить на этой конкретной задаче; для каждой правки дизайна менять его заранее не требуется.

Для дизайна лучше просить работающую вёрстку и снимки результата. Сгенерированная картинка может передать настроение, но сама по себе не проверяет реальные переносы текста, поведение календаря или размер кнопок.
