# Сервер ДЗ: аккаунты, синхронизация, Parakeet

Серверная часть отделена от публикации GitHub Pages. Ветка `codex/agent-sync`
не публикует приложение. Сервис по умолчанию слушает только `127.0.0.1:4286`.
Не открывайте Python HTTP-сервис напрямую в интернет: публичный вход — Caddy/HTTPS.

## Локальная проверка без моделей

Python 3.12+, Node 24. Синхронизация использует стандартную библиотеку Python.
База и аккаунты настоящие; модели нужны только при вызове агентских endpoints.

```sh
python3 -B -m unittest discover -s server -p 'test_*.py' -v
python3 -B server/app.py create-user --username artem
python3 -B server/app.py serve
```

В другом терминале:

```sh
DZ_DEV_PORT=4185 npm run dev:design
```

Проверьте свободные порты прежде, чем запускать процессы. При смене порта сервера
задайте `DZ_SERVER_PORT` серверу и `DZ_API_PROXY=http://127.0.0.1:<порт>` для Vite.
Старый локальный пилот на Mac остаётся на 4175/4176, его контракты не изменены.

Настройки → Аккаунт и синхронизация. Локальный адрес — `http://127.0.0.1:4185`.
Первый вход сохраняет исходную записную книжку и отправляет её задания.
Для проверки двух устройств используйте независимые профили браузера; второй
профиль должен войти в тот же аккаунт. Это не заменяет физическую проверку iPhone.

## Parakeet на Linux CPU

```sh
python3 -m venv .venv
.venv/bin/pip install -r server/requirements.txt
.venv/bin/python server/download_model.py
```

Понадобится `ffmpeg` в PATH либо абсолютный путь в `DZ_FFMPEG`.
Загружается Parakeet v3 INT8 из официальных материалов sherpa-onnx; готовые веса
около 640 МБ. Скрипт пишет SHA-256 скачанного архива, не перезаписывает каталог.
Модель открывается при первом запросе и остаётся в памяти. Только CPU, greedy decoding.
Запись до 60 секунд / 12 МБ, временные файлы удаляются, WAV — mono PCM16 16 кГц.
Тишина и пустая расшифровка отклоняются; это не гарантия отсутствия ошибок ASR.

Claude Code запускается существующим `scripts/voice-local/agent.py` через `claude -p`,
модель `haiku`, без инструментов и постоянной сессии, с JSON Schema. Понадобится
отдельный вход Pro/Max от системного пользователя сервиса. Прежде чем подключать
его на VPS, проверьте доступность региона и актуальные правила подписки.
OAuth-токены с Mac не копируются автоматически. Платный API не используется.

## Развёртывание после аренды VPS

Кандидат: Ubuntu 24.04 x86-64, 2 vCPU / 4 ГБ / 30–50 ГБ SSD, с возможностью увеличения.
Производительность на выбранном VPS ещё должна быть измерена.

1. Владелец предоставляет SSH-адрес и разрешённый способ входа. Приватный SSH-ключ
   оставляют файлом на компьютере; не вставляют в документы/переписку.
2. Создать непривилегированного пользователя `dz`, разместить код в `/opt/dz`,
   данные и домашний каталог сервиса в `/var/lib/dz` с доступом только для `dz`.
3. Установить Python, venv, ffmpeg, Caddy и Claude Code из официальных источников.
   Установить Python-зависимости в `/opt/dz/.venv`. Установить модель в `/var/lib/dz/parakeet`.
4. Скопировать и заполнить `dz.env.example` как `/etc/dz.env` с правами 0600.
   Секретов в примере нет. Войти в Claude от `dz` с тем же HOME, который использует сервис.
5. Создать личные аккаунты через CLI `create-user`: пароль вводится скрыто, не через
   аргументы процесса или shell history. Открытая регистрация для нескольких друзей не нужна.
6. Установить `dz.service`, проверить запуск, настроить DNS и Caddy из примера.
   Оставить наружу только SSH и HTTPS/HTTP для сертификата; 4286 остаётся loopback.
   `DZ_TRUST_PROXY=1` допустим только при таком входе через свой reverse proxy.
7. Проверить `https://<домен>/api/health`, CORS, вход, два устройства, ошибки сети,
   микрофон Safari/PWA, реальные Claude и Parakeet. На клиенте указать HTTPS-адрес
   в Настройках; адрес GitHub Pages и origin пользовательских данных не менять.
8. Публикация клиентского обновления и объединение веток — отдельное поручение.

`ProtectHome=true` закрывает личный home; Claude устанавливается в `/opt/dz/bin`
или другой доступный сервису каталог. Его токены находятся в `/var/lib/dz`, не в Git.
На GitHub Pages серверные процессы не запускаются. Куки третьей стороны не нужны:
клиент посылает отзываемую bearer-сессию в Authorization, CORS разрешает только
указанные origin. Токен хранится отдельно от экспорта заданий на устройстве.

## Протокол и миграции

- Notebook остаётся `version: 1` и в ключе `dz-next:v1`. Необязательные поля `sync`
  и `autoAdd` читаются новой версией; старые записи без них не переписываются при чтении.
- Первая привязка: копия `dz-next:before-account:v1`, затем очередь существующих ID.
  Другой аккаунт: текущая записная книжка сохраняется в локальном ключе аккаунта,
  новая копия получает только свои задания; возврат восстанавливает прежнюю очередь.
- Экспорт содержит Notebook, но не токен. Импорт переносит только задания. Отличающиеся
  записи с одинаковым ID получают новый ID; повторный импорт не создаёт дублей.
- Серверная схема `PRAGMA user_version=1`: users, sessions, tasks, operations.
  Инициализация повторяема. Более новая версия базы отклоняется.
- `POST /api/sync`: version=1, cursor, до 100 operations. Операция содержит id,
  taskId, baseRevision и task либо null (удаление). Ревизии выдаёт сервер.
- Повтор с тем же ID и содержимым безопасен; тот же ID с другими данными — 409.
  Неактуальная ревизия даёт конфликт, не переписывая другую версию.
- Ответ: accepted, conflicts, records и cursor. Задания и очередь сохраняются
  одним локальным JSON. Правка во время отправки остаётся в очереди.
- Вкладки новой версии подхватывают изменения localStorage через `storage`.
  Перед записью проверяется прежний снимок: обнаруженная устаревшая вкладка
  не перезаписывает данные и предлагает сохранить копию/перезагрузиться.
- Отметки удаления не очищаются; старое устройство не возвращает удалённые задания.
  Курсор, превышающий серверный, останавливает синхронизацию после старого restore.
  Нельзя исправлять это простым обнулением курсора без сверки копий.
- Старый клиент умеет читать основные задания, но не синхронизировать их. При откате
  обновлённого клиента отключите облачную функцию и сначала сохраните JSON: старая
  вкладка может записать снимок без актуальной очереди. Не держите разные версии
  одновременно открытыми для редактирования одной локальной записной книжки.

## Резервные копии

SQLite backup API копирует согласованную базу вместе с данными WAL:

```sh
python3 -B server/app.py backup --db /var/lib/dz/dz.sqlite3 --output /var/lib/dz/backups/dz-2026-10-01.sqlite3
```

Копия должна быть новым отдельным файлом. Для постоянного VPS настроить ежедневный
запуск с разными именами и хранение копий вне VPS. В них есть личные данные и хеши
доступа: ограничить права. Для восстановления остановить сервис, сохранить текущую
базу/WAL отдельно, восстановить согласованную копию и проверить аккаунты/курсоры.
При откате на старую копию возможны новые записи на устройствах: выполнить сверку,
не очищать их автоматически. Скрипт backup не развёрнут и расписание копирования
на VPS пока не настроено.

## Границы текущей приёмки

Без VPS не подтверждены Linux x86-64, HTTPS/DNS, systemd, лимиты на конкретном тарифе
и внешняя связь с iPhone. Локальные тесты не означают публикацию и телефонную готовность.
Технический браузерный стенд может возвращать фиксированный ответ разбора; это явно
отделяется от проверки настоящих моделей в отчёте ветки.
