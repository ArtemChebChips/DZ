# Аудит актуального PWA

Исходная точка: `c218703`, `codex/rebuild`, версия 1.23.57. Проверены `design/public/sw.js`, `design/register-sw.ts`, `vite.design.config.ts`, `design/index.html`; прочитан `scripts/assemble-pages.mjs` для проверки корня, `/next/`, `/legacy/` и `/codex/`. Прежние выводы про Google Fonts из версии 1.20.0 к текущему приложению не применяются.

## Подтверждённые проблемы и исправления

### PWA-01: повторный запуск ждёт сеть до 3,5 секунды

В исходном worker для навигации сначала выполнялся `fetch`; только после отказа или `AbortController` через 3500 мс использовался сохранённый `index.html`. При медленной, но формально доступной сети рабочая офлайн-копия поэтому не помогала быстрому запуску.

В Chrome на Mac запрос навигации искусственно задержан на 8000 мс. Три открытия нового окна после закрытия предыдущего дали примерно **3,6 секунды** в исходной сборке, **0,07–0,08 секунды** в исправленной. Точные значения сохранены в `audit/pwa-results.json`.

Теперь полностью установленная оболочка читается из своего кеша без ожидания сети. Новая версия загружается отдельно через регистрацию/проверку worker. При отсутствии кеша остаётся сетевой fallback; первый в жизни запуск без сети не обещается.

### PWA-02: новый worker не обслуживает старые хешированные assets

Worker использует `skipWaiting` и `clients.claim`, поэтому после установки новая версия управляет также прежними открытыми страницами. Их старые файлы отсутствовали в новом `FILES` и выпадали из кеширующего маршрута; после удаления прежней сборки с сервера такие запросы возвращали 404.

Добавлен поиск старых assets только в кеше собственного scope. Новый HTML всегда берётся из кеша текущей сборки; старый кеш используется только для точного URL хешированного asset. Автоматического reload нет: открытые формы и агентские черновики продолжают жить в прежнем документе. Новые открытия получают полностью закешированную новую оболочку.

Сценарий двух сборок: открыта форма v1 с введённым текстом; устанавливается v2 с новым именем JS, прежний JS удалён с сервера. Форма и объект-маркер старого документа сохраняются; старый JS возвращает 200 через новый worker; новая страница загружает JS v2. Это проверка браузера, не реального iPhone.

### PWA-03: разные сборки одной версии делили один кеш

Раньше имя кеша включало только scope и `package.version`. Сборка с тем же номером могла перезаписать HTML в кеше действующего worker до завершения перехода.

Сборщик теперь добавляет SHA-256 fingerprint шаблона worker, версии, списка и байтов файлов. Разные сборки разделены; имя scope остаётся частью ключа. Если установка неполной новой копии заканчивается ошибкой, удаляется только её вновь созданный кеш. Ранее существовавшие кеши и localStorage не удаляются.

Сценарий v3 с отсутствующим обязательным asset: установка завершается отказом, рабочая оболочка v2 остаётся доступна, её форма не теряет текст, кеш неудачной v3 удаляется.

### PWA-04: dev/demo могли заменять рабочую регистрацию

Регистрация теперь выполняется только в production и вне `?demo=1`. Worker пропускает демонстрационную навигацию в сеть, не меняя рабочую оболочку. В чистом demo-контексте проверены **0 регистраций и 0 кешей**. Уже зарегистрированный production worker на том же origin может по правилам браузера контролировать demo-страницу; это не удаляется ценой воздействия на рабочее приложение.

Регистрация отложена до `load`. Повторные проверки при возврате/возобновлении сети не выполняются чаще минуты; отклонения promise обработаны. Контроллер не вызывает перезагрузку страницы.

### PWA-05: сборщик worker игнорировал заданный outDir

`closeBundle` писал только в жёстко заданный `dist-design`, даже при переопределении каталога сборки. Теперь используется итоговая конфигурация Vite. Обычный `npm run build:design` и отдельная сборка с `--outDir /private/tmp/dz-next-pwa-outdir` прошли; в обоих выходных worker заменены все placeholders.

## Изоляция и офлайн

- Кеши адресуются полным `registration.scope` с разделителем после scope, поэтому root и `/next/` не смешиваются.
- При обновлении root оставлены кеш и контроллер `/next/`, а также посторонний кеш того же origin. После перезагрузки `/next/` использует собственный HTML, а не root v2.
- Навигации `/legacy/` и `/codex/` не совпадают с маршрутом оболочки root; их assets также не попадают под root `assets/`.
- Браузер был полностью закрыт, затем открыт с прежним persistent-профилем: проверен холодный запуск при медленной сети и при полностью отключённой сети. Значения и результаты — `audit/pwa-results.json`.
- `design/index.html`: внешних шрифтов и блокирующего стороннего CSS нет; manifest и иконки относительные. Текущие viewport и оформление системной полосы iPhone сохранены.

## Что намеренно не объявляется решённым

- **Физический iPhone недоступен.** Нужны холодное открытие установленного ярлыка, возврат из фона, запуск после обновления и проверка формы во время обновления на устройстве владельца. Измерения Chrome не являются цифрами производительности iPhone.
- При первом переходе со старого worker он ещё может выполнить прежнюю navigation-стратегию; ускорение становится доступно после успешной установки нового worker.
- Старые успешные кеши сохраняются для живых клиентов. Удалять «все кроме последних N» без знания версии открытых/замороженных вкладок небезопасно. Накопление остаётся ограничением; очистка в этом изменении касается только заведомо новой неудачной установки. При исчерпании квоты новая установка может отказать, сохранив рабочую версию.
- Cache-first означает, что при первом открытии после публикации может отображаться прежняя оболочка, пока новая сборка устанавливается в фоне. Автоматической перезагрузки с потерей черновика нет; следующий запуск получает обновление.
- Dev и production preview следует запускать на разных портах. Регистрацию уже существующего production worker на общем origin нельзя безопасно удалять из demo-кода ради теста.
- Публикация и переход старого установленного ярлыка с сервера пока не выполнялись.

## Воспроизводимость

Сохраняемый сценарий — `tests/browser/pwa.mjs`. Он извлекает baseline `c218703` через read-only `git archive`, собирает исходную и текущую версии во временном `mkdtemp`, создаёт синтетические v2/v3 и поднимает HTTP-сервер на свободном loopback-порту. После проверки временные файлы и профили удаляются. В ходе финальной проверки текущая версия — 1.23.58.

Запуск из корня репозитория после установки обычных зависимостей:

```sh
node tests/browser/pwa.mjs
```

Нужны Playwright и браузер. Если они доступны через bundled runtime, задать `DZ_PLAYWRIGHT_PATH` как абсолютный путь к каталогу пакета Playwright **или** его `index.mjs`/`index.js`, а `DZ_CHROME_PATH` — как абсолютный путь к исполняемому Chrome. По умолчанию используются пакет `playwright` и установленный им Chromium. `DZ_NODE_PATH` позволяет выбрать Node для дочерних сборок, `DZ_PWA_BASELINE` — изменить ревизию сравнения, `DZ_PWA_RESULTS` — путь итогового JSON. Никаких путей конкретного worktree/runtime в сценарии нет.

Для обновления fixture v2 меняет хешированное имя JS и build ID; fixture v3 добавляет отсутствующий обязательный asset. Производственные исходники/номер приложения ради этих fixture не подменяются. Все профили и данные синтетические, личные токены и аудиозаписи не используются.

Уточнение воспроизводимости: один поздний запуск harness не прошёл порог baseline, не сохранив отдельные значения. Причина этого единичного отказа не установлена и не объявляется багом приложения. Повтор с диагностикой прошёл. Чтобы результат можно было оценить при следующем отказе, baseline и current измеряются на отдельных loopback-origin с неизменяемыми каталогами; параметры принятого HTTP-запроса фиксируются до async I/O. Harness печатает каждый образец до assertions, сохраняет `workerStart`, `responseStart`, путь controller и число реально задержанных запросов. В baseline требуется участие worker и достижение задержанной сети, в current — участие worker без сетевого запроса оболочки. Длительность измеряется монотонными часами Node, а не системным `Date.now`. Пороги и неуспешные значения не отбрасываются и не подменяются.

## Источники

- [Service worker lifecycle — web.dev](https://web.dev/articles/service-worker-lifecycle): установка отдельной новой копии, риск `skipWaiting` для старых клиентов.
- [Update — web.dev](https://web.dev/learn/pwa/update): новый worker может управлять страницами старой версии.
- [Caching — MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching): cache-first оболочка обновляется с новым worker.
- [Cache — MDN](https://developer.mozilla.org/en-US/docs/Web/API/Cache): квота общего origin и ответственность приложения за обновление кешей.
