# Локальный агент и голосовой пилот: аудит без изменения источников

Сервер и смысловая логика пилота проверены без изменений: параллельный чат разрабатывает агент. Прочитаны все файлы `scripts/voice-local/`, `design/smart-input.ts`, `design/smart-input-panel.tsx`, dev-proxy в `vite.design.config.ts`, существующие `tests/smart-input.test.mjs` и относящиеся разделы обзора проекта. При общей приёмке основной агент изменил только контракт сохранения панели (await/занятость), а в `main.tsx` — завершение пакета и закрытие окна; это описано в `DATA.md`. Источники Python, распознавание и извлечение намерений не менялись.

## Воспроизводимые проверки

```sh
python3 tests/voice_local_test.py -v
```

Тесты используют стандартную библиотеку Python. Не создают сокеты, не запускают порт 4176, Claude, ffmpeg, реальную модель, загрузку весов или личные данные. `subprocess.run`, ASR-модули, модель, HTTP-потоки и ответ клиенту замоканы; WAV в проверке длительности синтетический и временный. Переменные окружения, глобальная блокировка и загруженная модель восстанавливаются после проверки.

Результат: **30 тестов, 26 успешных и 4 expected failures**. Expected failures проверяют желаемое поведение четырёх воспроизведённых отказов ниже; они не означают, что соответствующие проблемы исправлены. После исправления источников нужно убрать декораторы `expectedFailure` и повторить проверки. Неожиданный успех этих тестов также выделяется unittest, чтобы не забыть обновить статус.

Проверено:

- разрешённые Origin обоих локальных адресов и заголовок `X-DZ-Client`, отказ отсутствующему/чужому Origin;
- неизвестный endpoint, некорректная/нулевая/отрицательная/слишком большая Content-Length, отдельный лимит аудио;
- некорректный JSON и UTF-8, ошибки входных данных, generic 500 без приватных деталей, таймаут процесса 504;
- один активный запрос, ответ 409, освобождение lock после ошибок и после разрыва ответа клиенту;
- `Cache-Control: no-store` и безопасная обработка `BrokenPipeError`/`ConnectionResetError`;
- Pro/Max и отказ другому способу входа, валидация текста/контекста до subprocess;
- CLI-флаги без инструментов и сохранения сессии, таймауты auth 30 с и parse 90 с, фильтрация API-переменных и переключателей провайдеров;
- ошибки процесса, некорректный JSON CLI, структурно ошибочные результаты;
- ffmpeg-команда с ограничением 61 с, mono 16 кГц и таймаутом 20 с (только mock);
- принятие 60 с и отказ при большей длительности, повторное использование загруженной модели, отказ при тишине/ошибке декодирования, удаление временных synthetic-файлов.

## Подтверждённые проблемы для параллельного чата

### VO-01, P3: JSON не-объект получает 500 вместо ошибки входных данных

Разрешённый запрос `/agent/parse` с телом `[]` проходит `json.loads`. `agent.parse_tasks` затем вызывает `payload.get` без проверки объекта. Возникает `AttributeError`, а сервер сообщает 500 «Проверь запуск моделей», хотя виноват формат запроса.

Воспроизведение: `HandlerTests.test_known_bug_non_object_json_should_be_client_error`. Не требует Claude. Требуемое исправление — проверить `isinstance(payload, dict)` до `.get`, вернуть понятный `ValueError`/400. Для `null` и иных скаляров есть тот же путь отказа. Это обработка некорректного запроса; обычный интерфейс сейчас отправляет объект.

### VO-02, P3: код ошибки команды проверки входа игнорируется

После `claude auth status` не проверяется `status.returncode`. В синтетическом ответе с `returncode=1` и JSON, похожим на корректный Pro-вход, код продолжает запуск разбора. Подтверждено mock-воспроизведением; не утверждается, что реальная установленная CLI уже вернула именно такое сочетание.

Воспроизведение: `AgentTests.test_known_bug_failed_auth_command_should_not_parse`. Требуемое исправление — отказ при ненулевом returncode до доверия JSON. Источник не изменён.

### VO-03, P3: неожиданный верхний тип JSON CLI вызывает AttributeError

Если `auth status` либо основной CLI возвращает валидный JSON-массив вместо объекта, следующий `.get` вызывает `AttributeError`. Вызов через HTTP даёт generic 500, а не понятную ошибку проверки входа/ответа. Это воспроизведение неожиданного ответа внешней программы, не свидетельство неверного формата обычной успешной CLI.

Воспроизведение: `AgentTests.test_known_bug_wrong_auth_shape_should_have_actionable_error` и `test_known_bug_wrong_result_shape_should_have_actionable_error`. Требуемое исправление — проверить тип JSON-объекта перед `.get`.

## Замечания по frontend, ещё без аппаратной/браузерной приёмки

- Во время `Включаю микрофон…` показана кнопка «Отменить запрос», но её обработчик только вызывает `request.current?.abort()`. Pending `getUserMedia` не является этим fetch-запросом. По текущему управлению состоянием последующее разрешение микрофона может всё равно начать запись. Нужен отдельный флаг отмены открытия микрофона, проверяемый после получения stream; не выдавать чтение кода за проверку реального permission prompt.
- Повторный разбор создаёт новые предложения через `resolveProposal`, где `selected: true`. Исключённая ранее checkbox-карточка потому снова включается после уточнения. Перед сохранением пользователь видит результат, автоматического добавления нет. Следует согласовать с параллельным чатом сохранение исключений; поведение пока не обозначено как доказанный продуктовый баг, поскольку явного требования сохранения выбора между разборами нет.
- Cleanup вызывает `MediaRecorder.stop` только для `state === 'recording'`. Для внешне переведённого в `paused` recorder этого недостаточно, однако кнопки pause в текущем интерфейсе нет. Это защитное замечание, не воспроизведённый обычный пользовательский сбой.
- У клиента есть таймаут 130 с и abort. Он не прекращает уже запущенный серверный subprocess: это **прямо описано в README** и не записывается как новая ошибка.

## Предусмотренное поведение и ограничения

- Несколько видов следующей пары без указания вида требуют вопроса; лекция в смешанном расписании не должна молча считаться семинаром. День недели требует выбора абсолютной даты. Следующие занятия сегодня, которые уже начались, пропускаются.
- Клиент дополнительно проверяет 1–12 карточек, непустой текст до 4000 символов, ID предмета, тип/вид срока и настоящую дату. Сервер доверяет JSON Schema CLI сильнее; mock-проверки не доказывают качество смыслового извлечения.
- Подтверждённых каникул/переносов нет; `exceptionsKnown: false` корректно сохраняет эту неопределённость.
- В обычном редакторе ограничение текста и долговременное хранение имеют свою специфику; отсутствие повсеместного лимита в хранилище не объявляется багом голосового пилота.
- Нельзя приравнивать эти тесты к проверке реального Claude, Pro/Max-аккаунта, ASR, микрофона Safari/iPhone, шумов, реальной отмены permission prompt, соединения телефона с Mac или защищённого сервера. Никакая из этих систем здесь не запускалась.
- `start.command`, загрузчик, benchmark, probe и check-identifiers прочитаны, но не исполнялись: часть из них делает внешние запросы или обрабатывает аудио. Dev-proxy ведёт на loopback 4176, production Pages не подключён к нему.

Содержимое личного storage, реальные записи, переписки и токены не использовались и не сохранялись.
