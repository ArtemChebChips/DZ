# Как работать над «ДЗ» с GPT-6 Astra на Medium

Обновлено 21 сентября 2026 по официальным материалам OpenAI и текущим замечаниям владельца. Astra используется как помощник в Codex; AI API в приложение не добавляем. Ближайшие задачи — [план исправлений P1–P7](IPHONE_FIX_PLAN.md).

## Что проверено по официальным источникам

GPT-6 Astra поддерживает `medium`. Сохраняем выбранный владельцем уровень; это не обещание одинакового качества для любой сложности. Автоматически менять модель или уровень не требуется. [Описание модели](https://developers.openai.com/api/docs/models/gpt-6-astra).

Рекомендации для Astra: явно задавать ожидаемый результат и момент завершения работы, разрешать обычные действия внутри задачи, убирать противоречащие друг другу инструкции. Для кода объём проверок должен соответствовать изменению. [Руководство GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra).

Постоянные инструкции стоит держать короткими, а документы читать по задаче. Чрезмерно подробные рецепты и обязательное перечитывание всего проекта перед каждой правкой расходуют контекст и могут мешать работе. [OpenAI: Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

Отдельной обязательной формулы промпта для Medium в этих материалах нет. Деление на законченные небольшие этапы ниже — наш способ организовать работу над «ДЗ». Главное в запросе: что должно измениться для пользователя, критерии готовности, существенные ограничения и поручение проверить и выпустить результат.

## Как будем выполнять план

Один запрос запускает один этап P1–P7. У этапа уже есть контекст, ожидаемое поведение и проверки, поэтому пересказывать всё приложение не нужно. Модель должна довести этап до работающего результата, устранить найденные проблемы и проверить публикацию. Следующий этап — по следующему поручению, чтобы владелец мог посмотреть обновление на телефоне.

Требования к русскому языку, простому коду, данным, версии и Git находятся в `AGENTS.md`. Эти правила не нужно копировать в каждый запрос. Для iPhone различаем проверку в браузере и на настоящем устройстве. Если устройства у агента нет, он сообщает этот предел проверки и даёт короткий сценарий владельцу.

## Готовый запрос для первого этапа

```text
Выполни P1 из docs/IPHONE_FIX_PLAN.md в «ДЗ».
Исправь верхний отступ на iPhone и положение нижней навигации:
заголовки должны быть под системной областью, панель — на одном месте
в Задачах, Расписании и Настройках, без лишней полосы снизу.
Сначала установи причину смещения; сохрани выбранный вид A4 «Лист».
Рутинные решения принимай самостоятельно. Доведи этот этап до проверок,
устрани найденные проблемы, повысь версию, сделай коммит и push.
Проверь публикацию по старому адресу. В конце кратко укажи результат,
версию, коммит и что проверено в браузере, а что требует iPhone.
P2 пока не начинай.
```

## Запрос для следующих этапов

```text
Выполни P<N> из docs/IPHONE_FIX_PLAN.md.
Прочитай этот этап и связанные с ним части проекта. Реализуй описанное
поведение в выбранном дизайне, выполни критерии приёмки и проверки.
Обычные решения принимай самостоятельно и доведи работу до выпуска:
версия, коммит, push и проверка Pages по старой ссылке.
Обнови статус этапа в плане. В конце — короткий результат и ограничения
проверки. Следующий этап пока не начинай.
```

Заменить `<N>` на нужный номер. Содержание запросов по очереди:

| Этап | Что проверяет владелец после выпуска |
|---|---|
| P1 | Верхний отступ, стабильная нижняя панель, клавиатура |
| P2 | Сегодняшние пары при входе, календарь по кнопке, крупное время и кабинет |
| P3 | Собственный список выбора, отметка предмета, короткие названия |
| P4 | Синие семинары, зелёные лабы, задание внутри нужной пары |
| P5 | Заметка на любой день без привязки к паре |
| P6 | Тестовые задания на несколько недель и очистка только этих заданий |
| P7 | Согласованность вида и полный сценарий на телефоне |

## Если ошибка осталась после выпуска

```text
В версии [номер] после P1 осталось такое поведение:
[шаги: откуда открыл, какую вкладку нажал, что произошло].
Ожидалось: [что должно быть на экране].
Запуск: [ярлык iPhone или Safari], устройство/iOS: [если известны].
Найди причину и исправь этот сценарий. Проверь связанные действия,
затем выпусти обновление по правилам проекта. Сначала заверши это
исправление; следующую функцию пока не добавляй.
```

Скриншот или короткая запись экрана полезны, если положение элементов трудно описать, но не являются обязательными для начала диагностики. Агент сначала использует доступные данные и код.

## Если нужна новая доработка

```text
Добавь в «ДЗ» [конкретное действие пользователя].
Ожидаемое поведение: [2–4 наблюдаемых результата].
Сохрани [важные данные или вид]. Рутинные решения принимай сам.
Проверь затронутые сценарии, исправь найденные проблемы и выпусти
готовое обновление с коммитом, push и проверкой публикации.
```

Для исследования прямо просить план или анализ. Для реализации — сделать работающий результат. При новой просьбе о визуальных концепциях сначала используется ImageGen и выбор владельца; сейчас A4 «Лист» уже выбран, возвращаться к генерации без запроса не нужно.
